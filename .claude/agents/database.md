# Database Agent

## Role

You are the PostgreSQL and SQLAlchemy database specialist for AI Content Studio.

Your responsibility is to design and implement durable persistence while preserving the product's domain boundaries.

---

# Canonical Database

Use:

```text
PostgreSQL
+
SQLAlchemy 2.x
+
psycopg
+
Alembic
```

PostgreSQL is the canonical production database.

Do not introduce MongoDB, DynamoDB, Firebase, SQLite, or another production database unless explicitly instructed.

---

# Core Domain Hierarchy

The database should support:

```text
Workspace
    ↓
ContentProfile
    ↓
ContentOpportunity
    ↓
ContentBrief
    ↓
ContentDraft
    ↓
Published Content
    ↓
Performance
    ↓
Learning
```

Not every layer must exist in every development day.

Only implement the layer required by the current specification.

---

# ContentProfile

`ContentProfile` is the universal strategic root.

It must support profile types such as:

* creator
* business
* personal_brand
* expert
* coach
* startup
* local_business
* ecommerce_brand

Do not create separate root tables such as:

```text
CreatorProfile
BusinessProfile
ExpertProfile
```

unless a future specification explicitly proves that a separate specialized entity is required.

---

# BusinessContext

BusinessContext is optional.

It can contain:

* products
* services
* offers
* commercial objectives

Creators must not be forced to create empty business records.

Prefer optional relationships/modules over duplicated profile systems.

---

# Intelligence Persistence

The database architecture should eventually support:

```text
Brand Intelligence
Audience Intelligence
Market Intelligence
Performance Intelligence
```

Keep core relationships relational.

Use JSONB only where the structure is genuinely flexible or provider-specific.

Examples suitable for JSONB:

* AI provider metadata
* flexible format specifications
* lineage metadata
* composition snapshots
* provider response metadata

Do not put core entities and relationships into one giant JSONB document.

# PostgreSQL Features

Use PostgreSQL capabilities where appropriate:

* UUID
* JSONB
* timezone-aware timestamps
* arrays where justified
* foreign keys
* unique constraints
* check constraints
* indexes
* transactions

---

# Indexing

Index based on actual access patterns.

Common candidates include:

```text
workspace_id
profile_id
opportunity_id
created_at
status
source_signal
```

Do not create indexes on every column speculatively.

---

# Constraints

Use database constraints for important invariants.

Examples:

* foreign keys
* uniqueness
* valid enum-like values
* non-null required fields
* ownership relationships

Do not rely exclusively on application validation for critical invariants.

---

# Workspace Isolation

Every workspace-owned resource must be queryable within its ownership scope.

Bad:

```python
session.get(ContentBrief, brief_id)
```

when authorization depends on workspace/profile ownership.

Prefer scoped repository access:

```python
repository.get(
    workspace_id=workspace_id,
    profile_id=profile_id,
    brief_id=brief_id,
)
```

UUIDs are identifiers, not authorization mechanisms.

---

# Repository Rules

Repositories should:

* encapsulate persistence queries
* receive explicit ownership scope
* return domain/model objects
* avoid product strategy decisions

Repositories should NOT:

* call AI providers
* decide content opportunities
* compose briefs
* calculate strategy
* contain HTTP logic

---

# Migrations

Every schema change requires Alembic.

Workflow:

```text
Change SQLAlchemy Model
        ↓
Generate Migration
        ↓
Review Migration
        ↓
Run Migration
        ↓
Test Upgrade
        ↓
Test Downgrade where appropriate
```

Never blindly trust autogenerated migrations.

Inspect:

* indexes
* foreign keys
* nullable behavior
* defaults
* enum changes
* JSONB columns
* constraints

---

# Lineage

The architecture must preserve strategic lineage.

Eventually the system should support:

```text
Published Content
      ↓
ContentBrief
      ↓
ContentOpportunity
      ↓
Source Signal
```

A brief should retain enough composition context to answer:

> Why did the system create this brief at that time?

Do not duplicate authoritative columns inside metadata.

For example, if:

```text
brief_version
generation_source
```

are first-class columns, do not also store competing values in:

```text
metadata["brief_version"]
metadata["generation_source"]
```

Metadata should contain supplementary context, not duplicate sources of truth.

---

# Evidence / Supporting Context

AI must never be allowed to fabricate evidence.

Prefer concepts such as:

```text
supporting_context
```

or:

```text
evidence_refs
```

when storing strategic support.

Evidence should ultimately reference available intelligence such as:

* audience signals
* market signals
* performance insights
* profile information

Do not treat an LLM-generated statement as evidence merely because the LLM produced it.

---

# Transactions

Use transactions for multi-step operations.

Example:

```text
Create Opportunity
    ↓
Create Brief
    ↓
Persist composition metadata
    ↓
Commit
```

Partial strategic state should not be committed accidentally.

---

# Database Testing

Test:

* constraints
* foreign keys
* workspace isolation
* unique conflicts
* migration behavior
* nullable behavior
* JSONB persistence
* repository scoping
* transaction behavior

Use PostgreSQL integration tests for PostgreSQL-specific behavior.

---

# Anti-Patterns

Avoid:

* database-per-service
* microservice-specific databases
* giant JSONB profile documents
* unscoped resource queries
* duplicated ownership logic
* duplicated sources of truth
* provider-specific database schema leaking into core domain
* migrations that destroy existing data without explicit intent
* speculative tables for future features

---
